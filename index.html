Case Study 01

Sliding-Window Deque vs. Token Bucket in High-Burst Gateways

Throughput: 85,000 req/sec Complexity: O(log N)

Fixed-window counters permit 2x traffic bursts across window boundaries (e.g., 100 requests at 00:59 and another 100 at 01:00 results in 200 requests within two seconds). While Token Bucket regulates long-term burst rates, it allows micro-bursts that degrade downstream payment providers.

The Architecture: We implemented an in-memory double-ended queue (deque) using Redis Sorted Sets with epoch millisecond scores:

  • Atomic eviction: ZREMRANGEBYSCORE key 0 (now - window)
  • Atomic insertion & count: ZADD key now uuid followed by ZCARD key
  • Pipelines executed under 2.1ms p99 latency via connection multiplexing.

Case Study 02

Zero-Drift Financial Ledgers: Enforcing Debit/Credit Invariants

Integrity: ACID Strict Concurrency: Optimistic Versioning

In digital economies and fintech platforms, mutating account balances directly in place via UPDATE accounts SET balance = balance - 100 causes catastrophic reconciliation errors under concurrent transactions and network dropouts.

The Immutable Solution:

  • Append-Only Journals: Account balances are never overwritten; they are materialized from immutable ledger entry postings.
  • Mathematical Invariant: Every transaction encapsulates an array of balance shifts where Σ Debits + Σ Credits = 0.
  • Optimistic Concurrency Control (OCC): Uses row versioning (RowVersion) to reject conflicting simultaneous writes with an immediate retry policy.

Case Study 03

Distributed Idempotency & Split-Brain Protection with Redis SETNX

Lock TTL: 1500ms + Auto-renewal Safety: Random Nonce Validation

When distributed consumers read from message brokers like Apache Kafka, network blips or long GC pauses can cause broker partitions to rebalance. Consumers might process a duplicate message while the previous worker is still finalizing its write.

The Mitigation Protocol:

  • Atomic distributed acquisition using SET resource_key random_nonce NX PX 1500.
  • Only the consumer holding the valid random_nonce can release the lock, verified via an atomic Lua script: if redis.call("get", KEYS[1]) == ARGV[1] then return redis.call("del", KEYS[1]) else return 0 end.
  • Eliminates lock-stealing race conditions entirely across distributed service replicas.
// Atomic Lock Release (Lua)
-- Distributed Lock Release Script
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
else
    -- Lock expired or held by another node
    return 0
end
